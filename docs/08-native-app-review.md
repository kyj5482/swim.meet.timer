# 08. 네이티브 앱 전환 검토 (앱 전문가 관점)

현재 PWA(docs/app/index.html)를 그대로 포장하지 않고, 아래 결정에 따라
**React Native로 재구축**한다. 디자인 언어(다크·레인색·대형 타깃)는 유지하되
구현은 전면 네이티브.

## 1. 왜 PWA로는 안 되는가
- **볼륨 키 제어 불가** — 브라우저는 하드웨어 키를 앱에 넘기지 않는다.
- iOS PWA는 wake lock·오디오·백그라운드 동작이 불안정, 설치 경로가 낯설다.
- 스토어 배포·IAP 구독(수익 모델)·푸시가 사실상 불가능.
- 터치 → JS 이벤트 경로의 지연 변동이 커서 1/100초 신뢰도가 흔들린다.

## 2. 프레임워크: React Native + Expo (custom dev client)
- 기존 엔진·문서가 전부 TS → `packages/timer-core` 그대로 재사용(재작성 리스크 0).
- EAS Build로 Mac 없이 iOS 빌드 가능(바이브코딩 친화).
- Flutter 대비: 코드 재사용·생태계(RevenueCat, Powertools 등 TS 통일) 우위.
- Expo Go로는 부족(네이티브 키 이벤트 모듈 필요) → **custom dev client** 전제.

## 3. 1/100초 정밀도 설계 (핵심)
정확도를 결정하는 것은 클락이 아니라 **입력 캡처 시점**이다.
- 탭: `onPressIn` + `e.nativeEvent.timestamp`(OS가 터치를 캡처한 시각, JS 처리
  지연과 무관). 엔진에는 이 시각을 주입 — `performance.now()`를 핸들러에서 다시
  읽지 않는다.
- 볼륨 키(Android): `KeyEvent.getEventTime()`(uptimeMillis, 모노토닉)을 네이티브
  모듈에서 그대로 전달. 커널 캡처 시각이므로 최상급 정밀도.
- 렌더는 표시일 뿐: 시계는 rAF 60fps, 입력 경로와 완전 분리(기존 §3.1 원칙 유지).
- 목표 예산: 탭 캡처 오차 < 20ms, 표시 지연 < 50ms.

## 4. 볼륨 키 제어 — 플랫폼 현실
| | Android | iOS |
| --- | --- | --- |
| 볼륨 키 가로채기 | ✅ Activity `onKeyDown` 오버라이드, 공식적으로 허용 | ❌ 공개 API 없음. 우회(오디오 세션 감시)는 App Review 2.5.9 거절 사유 |
| 대안 | — | 블루투스 리모컨/키보드(스페이스·미디어키 → LAP), Apple Watch 컴패니언(후순위) |
- 결론: **Android = 볼륨 키 LAP 정식 기능**, iOS = 화면 대형 LAP + BT 리모컨 지원.
  마케팅 문구도 플랫폼별로 분리한다. (심사 거절 리스크를 안고 iOS 볼륨 훅을
  넣지 않는다 — 스토어 제거가 최악의 시나리오.)

## 5. 유지·강화할 기존 강점
- 단일 LAP + 레인 직접 탭 이중 입력, 라운드 단조매칭(§3.3), 측정 후 배정(§3.6),
  저신뢰 맞바꾸기 — 전부 timer-core로 이식 완료.
- wake lock → expo-keep-awake, 햅틱 → expo-haptics(젖은 손 피드백 강화).
- 오프라인 우선: IndexedDB → **expo-sqlite**(트랜잭션·마이그레이션 정식 지원).

## 6. 무료/구독 경계
- 무료: 타이머 전체, 로컬 기록·추세, CSV 내보내기, 타겟 1개 달성 %.
- 구독(AI 코치): 클라우드 동기화·공유, 궤적/가속도 분석, 주간 리포트, 포트폴리오,
  코치 전달. — "측정은 영원히 무료"를 명시(PWA의 Cloud 문구 계승).

## 7. 기존 PWA의 처우
- `docs/app/`은 데모·마케팅 페이지로 유지(GitHub Pages). 신규 기능 추가 금지.
